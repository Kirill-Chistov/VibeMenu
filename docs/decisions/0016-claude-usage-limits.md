# 0016 — Claude usage limits (opt-in; local Desktop cache + Claude Code status line)

- **Status:** Accepted — v0.3 feature (experimental; two local sources)
- **Date:** 2026-07-09
- **Deciders:** Kirill Chistov (product owner; requested the feature, authorised reading Claude's local
  app/cache data, set the opt-in/experimental/honest/local-only/read-only conditions). Researched &
  implemented by Claude Code under the owner's authorization.
- **Builds on / relates to:** [`0008`](0008-claude-heartbeat-detection.md) (opt-in hook + VibeMenu-owned
  files pattern), [`0014`](0014-enhanced-desktop-titles.md) (opt-in, default-off reading of best-effort
  local data with a whitelist DTO), [`0006`](0006-lightweight-resource-budget.md) (lightweight budget).

## Context

We want a compact "Claude Limits" menu section showing the user's **real** Claude usage limits — the
5-hour and weekly windows with a used-percentage and a reset time — matching the app's usage-bars
design. Hard constraint: this must be **real** data (not token-count estimation, not a manual counter,
not a made-up cost tracker) obtained **locally** with **no network, no cookies, no API keys, no
scraping, no telemetry**, or we do not ship it. The owner's primary want is the **Claude Desktop**
usage bars; Claude Code CLI users should be covered too.

A two-pass investigation (metadata/field-names only) mapped every option:

1. **Token-count estimation** — tools like ccusage sum tokens from `~/.claude/projects/*.jsonl` and
   compare to hardcoded plan ceilings. An **estimate**, not the server's real quota — **forbidden**.
2. **Network usage API** — the menu-bar apps (ClaudeMeter, Usage4Claude, …) call
   `api.anthropic.com/api/oauth/usage` with the OAuth token from `~/.claude/.credentials.json`, or the
   web API via the claude.ai cookie. Real, but a **network call with an auth token/cookie** — **forbidden**.
3. **Claude Desktop HTTP cache** *(chosen — primary)* — Claude **Desktop** (an Electron/Chromium app)
   fetches `GET https://claude.ai/api/organizations/{org}/usage` when it renders Settings → Usage, and
   Chromium stores the response in its on-disk "Simple Cache"
   (`~/Library/Application Support/Claude/Cache/Cache_Data/<hash>_0`). The body is **zstd-compressed**
   (`content-encoding: zstd`) and carries the real `five_hour`/`seven_day` utilisation + resets and a
   `limits[]` array (which can include **per-model** weekly rows). Reading it is local, real, and needs
   **no** network/cookie/token. The catch is that macOS ships **no zstd** (Apple `Compression` does
   zlib/lzfse/lz4/lzma/brotli only; no system `libzstd`), so decoding requires a bundled decoder.
4. **CLI-native statusLine `rate_limits`** *(chosen — secondary)* — Claude Code (v2.1.80+) pipes a
   `rate_limits` object on the **statusLine command's stdin JSON**: `five_hour` and `seven_day`, each
   with `used_percentage` (0–100, the same value the in-app `/usage` view shows) and `resets_at` (epoch
   seconds). Real, local, zero-network — but Claude Code only, and all-models only (no per-model rows).

## Decision

Ship an **opt-in, default-off, clearly-labelled Experimental** "Claude Limits" section fed by **both**
local sources, chosen in Settings:

- **Claude Desktop** (option 3) — read + zstd-decode the local usage-cache entry. Primary source; the
  only one that can show per-model weekly rows.
- **Claude Code** (option 4) — the opt-in statusLine capture (ADR-0008-style shim → VibeMenu-owned file).
- **Automatic** (default) — prefer a **fresh Desktop** snapshot (richer); else a **fresh Claude Code**
  snapshot; else whichever stale snapshot is newer. Never present stale data as live.

### The zstd dependency (new)

Decoding Desktop's cache needs a zstd decoder and macOS has none. Per the project rules we do **not**
shell out to a `zstd` binary, use Homebrew, add a network fallback, or take a GPL/AGPL dependency. We
**vendor the official, decompression-only Zstandard** as a SwiftPM C target (`Sources/CZstd`):

- **What:** the official single-file amalgamation `zstddeclib.c` (decode-only — contains **no
  compressor**) plus the unmodified `zstd.h` / `zstd_errors.h` and a module map.
- **Version / provenance:** zstd **v1.5.6**, commit `794ea1b0…`, generated by zstd's own
  `create_single_file_decoder.sh`. Reproducible; see [`Sources/CZstd/README.md`](../../Sources/CZstd/README.md).
- **License:** zstd is dual **BSD-3-Clause OR GPLv2**; we use the **BSD-3-Clause** option (no copyleft).
- **Safety:** a thin Swift wrapper (`Zstd.swift`) uses only the stable streaming API
  (`ZSTD_decompressStream`) so it stops at the frame boundary (Chromium appends its own metadata after
  the frame) and **caps decompressed output** (8 MiB) to defend against a decompression bomb. Input is a
  local file only; there is no network path into the decoder.

Both `swift build` and the Xcode `.app` build compile and link `CZstd` (it is a dependency of the local
`VibeMenuCore` package, which the app links).

### Normalised model & fields read vs. ignored

`VibeMenuCore` owns a source-independent model (`ClaudeUsageLimit{,Kind,Snapshot,Status,Source}`,
`ClaudeUsageLimitSourceMode`). Rows: the 5-hour window, the weekly all-models window, and — from Desktop
only — per-model weekly rows ("Weekly · Opus"). Each row is a used-percent (clamped 0…100), an absolute
reset time, an optional model group, a source, and a captured-at timestamp.

- **Read (whitelist).**
  - *Desktop:* only `limits[].{kind, group, percent, resets_at, is_active, scope.model.display_name}`
    and, as a fallback shape, top-level `five_hour`/`seven_day`
    `{utilization|used_percentage|percent, resets_at}`. Plus the HTTP `Date` header (for staleness).
    The `Decodable` DTO has **no property** for anything else.
  - *Claude Code:* only `rate_limits.{five_hour,seven_day}.{used_percentage,resets_at}`, `session_id`,
    `version`.
- **Ignored (never read, stored, or displayed):** the payload's `spend`/cost/billing, the **org UUID**
  (never persisted), the `scope.model.id`, prompt/response text, transcripts, cwd/paths, tool I/O — and
  for Claude Code the same, enforced twice (shim parser + reader DTO). VibeMenu shows **no**
  money/cost/message-count row.

### Real Desktop payload shape (verified) & normalisation

Verified against the live cache, the real `/usage` body names its windows differently from the initial
guess, and this drives the normalisation rules (`ClaudeDesktopUsageParser`):

- **`kind`** is `session` (the 5-hour window), `weekly_all` (weekly across all models), or
  `weekly_scoped` (a per-model weekly row). `windowKind` maps `session → fiveHour` and the two
  `weekly_*` names → `sevenDay`, alongside the older `five_hour`/`seven_day`/`5h`/`7d` variants.
- **`is_active`** flags only the single currently-binding limit `true`; the other (equally real)
  windows are `false`. It is therefore **read but NOT used as a display filter** — filtering on it
  would drop the live 5-hour and weekly-all rows (this was the original "only one weekly row" bug).
- **Per-model identity** comes from `scope.model.display_name` (e.g. "Fable"), **not** the `group`
  field, which is a generic bucket (`"weekly"`/`"session"`). Generic buckets normalise to `nil`, so the
  all-models weekly row renders the plain label **"Weekly"** — never the duplicate "Weekly · Weekly"
  (the original second bug). A real per-model row renders "Weekly · Fable". The model `id` is ignored.
- **Menu row order** is 5-hour, then weekly all-models, then per-model weekly rows alphabetically; the
  section sits **above** the Session Radar in the menu.

### Freshness / staleness / last-known-good

The Desktop cache body is **intermittent**: Chromium serves a full 200 body, then revalidates with
**empty 304** bodies until the next refresh, and the entry is LRU-evictable. So the Desktop reader:
(a) scans only *small, recently-modified* entries (the usage entry is a few KB, rewritten often),
throttles rescans, and picks the freshest **decodable** body; and (b) VibeMenu persists the last good
Desktop decode to a **VibeMenu-owned** file (`…/VibeMenu/ClaudeUsage/desktop-snapshot.json`, normalised
rows only — no org UUID, no raw payload) so an empty-cache tick shows the last numbers **aged and
flagged stale** rather than blinking to "unavailable". The model has explicit `.fresh` / `.stale` /
`.unavailable` states (10-min default): stale shows an "as of Xm ago" note; no data shows a quiet
guidance line — **never a fabricated bar, never stale-as-live**. Reset *countdowns* stay correct
regardless, being derived from the absolute `resets_at`.

### One-click install for Claude Code (a deliberate, narrow posture change)

Claude Desktop needs **no** setup (auto-detected, read-only). The Claude Code source needs a
`statusLine` command; the owner chose in-app one-click install over manual. Because there is a single
statusLine slot, install **composes**: VibeMenu's shim wraps any existing command (base64 in the shim's
`--wrap` arg) and re-emits its output, so the terminal status line is unchanged; uninstall restores the
original. This is the **first** time VibeMenu writes to `~/.claude/settings.json` — constrained to be
safe: **strictly opt-in, preview-gated, a timestamped backup before every write, fully reversible, and
the risky compose/uninstall logic is pure and unit-tested** (`StatusLineInstaller`). Manual install
remains documented (`Support/ClaudeUsage/README.md`).

## Why not the other sources

- **No token estimation** — an estimate, not the real quota; explicitly forbidden.
- **No network / OAuth token / cookie** — violates the hard no-network/no-secrets invariant; VibeMenu
  never reads `~/.claude/.credentials.json` or a claude.ai cookie.

## Privacy

- **Local-only, read-only.** No network, no cookies, no API keys, no auth-token extraction, no scraping,
  no telemetry. VibeMenu never writes to, or deletes, Claude Desktop's cache.
- **Whitelist only**, enforced by the `Decodable` DTOs (Desktop) and twice for Claude Code (shim +
  reader). No transcripts, prompts, responses, paths, cost, spend, billing, or org UUID reach the model.
- **VibeMenu-owned persistence only** — normalised snapshots, never raw cache payloads or the org UUID.
- **Off ⇒ zero file I/O.** The provider checks the preference before reading either source.
- **settings.json writes** are opt-in, preview-gated, backed up, reversible, and touch only `statusLine`.
- **Tests use only synthetic fixtures** (hand-written JSON; zstd frames generated offline from fake
  data). No real account data or real cache payload is committed.

## Risks

- **Desktop format/version drift & fragility.** The cache path, Simple Cache layout, zstd encoding, and
  JSON shape are all undocumented and Claude-controlled; the body is intermittent and LRU-evictable.
  Mitigated by defensive byte-parsing (never trusts private cache internals), fail-closed `.unavailable`,
  last-known-good persistence, the honest Experimental framing, and the Claude Code fallback source.
- **Vendored C decoder.** ~900 KB of audited BSD zstd. Mitigated by decode-only scope, the streaming
  API, an output cap (bomb guard), local-only input, and being the official reference decoder.
- **Claude Code availability gaps.** `rate_limits` is Pro/Max-only, interactive-only, post-first-response,
  version-fragile — surfaced as an honest status, not an error.
- **settings.json editing.** Mitigated by opt-in + preview + backup + reversibility + pure/tested logic.
  A **second-model review of the decoder wrapper, cache parser, and install adapter is advised** before
  public release (CLAUDE.md "second model" rule).

## Future: Codex / other providers / more per-model rows

`ClaudeUsageLimitSource`/`Kind`/`SourceMode` are enums and the UI iterates the limits array, so a new
source is additive (a Codex statusline/hook capture would add a source; more per-model rows are additive
`ClaudeUsageLimit` values with a `group`). No architectural change needed.

## Testing plan (all synthetic / fake data)

- **Model:** percent clamp (incl. NaN/±inf → 0), fraction/percent text, severity, reset formatting,
  per-model `group`/`displayLabel`/`id`/`sortKey` ordering, fresh/stale/unavailable + "as of Xm ago",
  Codable round-trip, source display names.
- **zstd:** decode a synthetic frame; reject garbage/empty/truncated; ignore trailing bytes after a
  frame; enforce the output cap (bomb); frame-scan skips leading junk.
- **Desktop parser/reader:** both JSON shapes; `limits[]` preferred over windows; forbidden
  spend/cost/org fields never surface; inactive rows skipped; window-kind mapping variants; group
  normalisation/prettify; ISO + epoch `resets_at`; Chromium entry recognition + `Date` header parsing;
  full compressed-entry decode; empty (304) entry → nil; directory scan (found / missing / empty /
  keeps-last-good / throttle).
- **Selection & store:** mode routing; Auto fresh-Desktop→fresh-ClaudeCode→newer-stale; Desktop
  empty-cache fallback to stored last-good (flagged stale); snapshot store save/load/round-trip.
- **Installer & shim:** command encode/decode; detect/compose/uninstall/preview; embedded-shim ↔
  Support-file sync; real shim subprocess → file → reader; whitelist-only (no cost/transcript/cwd leak).
- **Menu visibility:** the section's dividers, with the two-section behaviour unchanged when off.

## Status of implementation

Implemented behind the default-off `showClaudeLimits` preference with a source picker (Auto / Claude
Desktop / Claude Code). `swift build`, `scripts/test.sh` (376 tests), and the `.app` `xcodebuild` all
pass; the vendored decoder is linked into both builds. The **Desktop pipeline was verified against the
real local cache** at dev time (decoded the live 5-hour + weekly rows in ~27 ms over ~1,500 cache
files) — no real data was committed. The live popover was not launched (a second instance would
duplicate the owner's menu-bar item), so SwiftUI bar/divider placement remains a manual smoke-test step.

**Post-implementation correction (2026-07-09).** A re-check against the live cache showed the Desktop
normaliser was dropping rows: it filtered on `is_active` (which the real payload sets `false` on the
base windows), never mapped the real `session`/`weekly_all`/`weekly_scoped` kinds, and read the generic
`group` bucket ("weekly") as a model name — so the section showed a single mislabelled "Weekly · Weekly"
row and no 5-hour row. Fixed per the "Real Desktop payload shape" rules above: map the real kinds, stop
filtering on `is_active`, take the model from `scope.model.display_name`, collapse generic groups to nil
(the all-models row is now plain "Weekly"), and a defensive `displayLabel` guard so "Weekly · Weekly"
can never render even from an already-persisted snapshot. The Claude Limits section also moved **above**
the Session Radar; divider logic in `MenuVisibility` was rebuilt as "a divider above each visible
section that has one above it" so no combination doubles or strays.
