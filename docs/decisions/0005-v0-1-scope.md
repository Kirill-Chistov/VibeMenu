# 0005 — v0.1 scope: what's in, what's explicitly out

- **Status:** Accepted
- **Date:** 2026-07-02
- **Deciders:** Kirill Chistov (product owner).

## Context

The single biggest risk for a first native app is overbuild. The adjacent spaces — system
monitoring and AI usage tracking — are saturated and mostly free/open-source. VibeMenu's
wedge is the automation loop between agent activity and power management. v0.1 must be the
smallest build that proves that loop is reliable and trustworthy, and nothing more.

## Decision

**v0.1 is limited to:**

1. **Thermal pressure / status** — `ProcessInfo.thermalState` glance
   (nominal/fair/serious/critical); public API, no exact temperatures.
2. **Claude activity / session view** — working / idle / waiting, from process presence
   and session-file **metadata** only (never transcript contents).
3. **Sleep-prevention loop** — a public power assertion held while an agent works,
   released immediately when the agent is no longer active, with manual force-awake / force-off.
4. **Lightweight menu-bar UI** — a small `MenuBarExtra` status item + dropdown.

**v0.1 explicitly excludes:**

- **Full Codex support** — the architecture leaves room for it (agent-agnostic
  `AgentMonitoring`), but it is not implemented in v0.1.
- **Clamshell / lid-closed mode** — deferred; needs root + guardrails + its own ADR.
- **Exact temperatures** — no per-chip SMC keys; `thermalState` only.
- **Fan control** — a hard no (see below and [`0006`](0006-lightweight-resource-budget.md)).
- **Dock / app-switcher replacement** — out of scope, unrelated to the wedge.
- **Usage / quota dashboard** — not built; at most a thin optional read-only strip later.

## Consequences

- The core skeleton in this repo reflects exactly this scope: a real, tested
  `AutomationPolicy`, and protocol+stub seams for `AgentMonitor`, `PowerAssertionManager`,
  and `SystemStatus`. Excluded features exist only as `TODO`s / future ADR references, not
  code.
- **Fan control is a hard, indefinite "no"** and must never be built unless the human
  product owner explicitly reverses this decision in a new ADR. It requires root, the OS
  thermal governor overrides it, and getting it wrong risks hardware.
- Codex support and clamshell each get their own ADR when the time comes; neither may leak
  into `VibeMenuCore`.
- Scope creep into monitoring/usage-dashboard territory is treated as out of scope by
  default.

## Alternatives considered

- **Ship the all-in-one utility (monitor + usage + keep-awake + dock).** Rejected: five
  fronts against polished, mostly-free incumbents — the classic first-app overbuild trap.
- **Include Codex in v0.1.** Rejected: doubles the fragile activity-detection surface
  before the Claude loop is even proven.
